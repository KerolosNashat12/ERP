Repeating costs: daily, weekly, monthly and yearly

THE ASK
The owner, looking at the repeating-cost dialog: "can you please enhance this
function to be have a type (Monthly - weekly - and so on)". It only ever asked
for a day of the MONTH, because the engine behind it stepped one month at a
time and keyed each entry YYYY-MM.

FOUR FREQUENCIES, AND WHAT EACH ONE NEEDS
  daily     nothing.
  weekly    a day of the week - "every Friday", not "every 7 days from
            whenever I created this". A drifting weekday is a bug nobody can
            name.
  monthly   a day of the month, clamped. UNCHANGED, including its key.
  yearly    a day and a month.
The form shows only the fields the chosen frequency uses, and the server
stores NULL for the ones it does not - so a template switched from weekly to
monthly cannot keep a weekday that something later misreads.

WHAT DOES NOT CHANGE, AND WHY IT MATTERS MOST
Monthly keeps the YYYY-MM period key exactly. Every entry every existing
template has already posted carries that key; a new shape would make all of
them look unposted and offer the whole history again. There is a test that
inserts a template using only the columns that existed before this release -
the shape of every row in the live database - and checks its dates, its months
and its already-posted entries come out identical.

Catch-up is now about a year per frequency (daily 366, weekly 53, monthly 12,
yearly 2) instead of 24 months. Nothing is lost: the oldest are offered first
and the next batch appears as they are posted.

NO CHECK CONSTRAINT ON THE FREQUENCY COLUMN, ON PURPOSE
SQLite would accept one. A CHECK on a live table cannot gain a new value
without rebuilding the table under a trading shop - this project paid for that
lesson once already with sale_payments.method. A fifth frequency should be one
line. The list lives in public/shared/recurrence.js, which the engine, the API
validator and the browser's picker all read, so an unknown value cannot arrive
from outside.

THREE BUGS FOUND WHILE BUILDING IT
- A SEMICOLON IN A SQL COMMENT cuts a CREATE TABLE in half. The shared schema
  string is applied by splitting on ";", and that splitter cannot see comments,
  so an ordinary English semicolon in a note about a column made the migration
  fail at BOOT with "incomplete input". Same family as the backtick that cannot
  appear in a schema.js comment. Now fenced for every shared SQL string.
- Number(null) IS 0, AND 0 IS SUNDAY. Reading the weekday column with Number()
  alone turned "no weekday saved" into a confident Sunday, so a weekly template
  created without one would have repeated on Sundays instead of on its own
  start day. Absence is tested before coercion now, in both places that read it.
- hidden DID NOT MEAN HIDDEN. The attribute loses to `.field { display: grid }`,
  so hiding a form field left it on screen while every script was told it was
  hidden. This codebase has met that three times now and patched it one
  selector at a time twice; there is one global rule for it now. Found only
  because the browser check measured pixels rather than asking the code what it
  had intended.
