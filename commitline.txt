Exchanges: set the replacement's price, or take money off it

THE ASK
"حد جه يرجع استرونجر بـسوفاج، واسترونجر كانت بـ200 وسوفاج 500 - مش لازم
السيستيم يجبرني انها تفضل 500، لا أقدر أغير فيها أو أحط خصم"
And then: "خلي الخصم فلوس مش نسبة".

WHAT IT DID
The replacement was priced by the shelf and by nothing else. A 500 bottle
going out against a 200 one coming back was 500, and the only way to charge
anything else was not to use the exchange screen at all.

WHAT IT DOES NOW
The replacement row has a PRICE box and a DISCOUNT box, the discount in money
rather than as a rate. Both are optional: a line nobody touches is priced by
the shelf exactly as before, offers included. The row shows what it is
actually charged with what it was marked at underneath, so the shop can see
what it gave away.

Sending nothing changes nothing - the untouched path is fenced by its own test
so a screen that starts sending a price for every line cannot slip through.

A SECURITY HOLE FOUND AND CLOSED ON THE WAY
`sales.discount` decides who may change a price or discount a line. It was
enforced by DISABLING two boxes in the till's browser and NOWHERE ELSE. The
server never checked. So any cashier - every cashier has `sales.create` -
could post a sale carrying any `unit_price` it liked and the server wrote it
down: a 1,200 bottle for 1, and the books balance. The exchange screen was
about to become a second door to the same thing.

It is checked once now, on the write path every door leads to, and it covers a
typed price, a line discount and a manual discount on the header. An internal
caller with no actor is trusted code and passes; only a person who HAS a
permission list and lacks the code is refused. Fenced in pentest.test.js with
its control: the same four requests from the administrator must still succeed.

NO DATABASE CHANGE
Audited after the fact rather than assumed. A replacement is a sale line, and
sale_lines has carried unit_price, list_price, discount_percent and
discount_amount from the beginning; the columns were dumped from a freshly
migrated database and the values read back out of them in a test. No
migration, no new column, nothing to backfill.

ONE BUG THE TESTS MISSED AND A SCREENSHOT CAUGHT
Typing a price redrew the settlement strip but NOT the row it came from, so
the strip said 400 while the row beside it still said 500 - two numbers for
one line, on screen at once, and the cashier reads the row. Redrawing the
whole table would have taken the focus out of the box being typed into, so the
row refreshes its own cell in place. The browser check now reads the ROW as
well as the strip; it only looked at the strip before, which is why it passed
on a screen that plainly disagreed with itself.

Also fixed in that check: it searched for the replacement by NAME, so a
previous run's exhausted product was picked and the exchange failed with
"insufficient stock" for a product it had stocked seconds earlier. It matches
its own SKU now, and reports the toast when nothing is recorded rather than
leaving the reason to be guessed.
